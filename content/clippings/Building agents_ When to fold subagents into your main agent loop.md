*如果你在 Claude Platform 上构建了包含多个子智能体的智能体，可查看哪些子智能体适合用我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)并入主智能体循环。它会运行一个引导式工作流，用于识别你的模式、评估替代方案，并验证最佳方案。其中包含一个演示，你可以在模拟系统上先行试用，再用于你的真实智能体。*

子智能体（subagents）——拥有自己的上下文窗口、工具和指令，[由协调者编排](https://claude.com/resources/articles/multi-agent-coordination-patterns)的智能体——是智能体设计的核心组成部分。它们在验证、并行工作和模块化权限管理方面很有效。我们在用 Claude Platform 构建的许多自有智能体中都在使用它们，例如我们的[多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。

不过，最近应用 AI 团队（Applied AI team）发现了一种企业智能体部署模式：这些部署通过把路由器（router）、规划器（planner）和领域子智能体并入主智能体循环而获益。在[我们对若干企业部署的对比](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents#:~:text=In%20our%20comparisons%20across%20several%20enterprise%20deployments,latency%20per%20task)中，[带技能的单一智能体](https://claude.com/resources/articles/building-agents-with-skills-equipping-agents-for-specialized-work)在质量上常常同时优于“一个提示词包打天下”的设计和子智能体设计，而且每个任务的成本和延迟往往更低。

例如，一家公司发现，其面向客户的智能体中的十几个专家子智能体，让统一且符合品牌调性的体验难以维持，还增加了损害用户体验的延迟。

我们还经常看到一些被提议的智能体设计遵循一条常见的演进路径：意图分类器、固定的多步推理流水线、按用户分群划分的桶、独立的推荐分支，最上面再套一个多智能体编排器。

在这些情况下，反馈往往是：这套结构的大部分都在做模型如今已不再需要它做的事，而一个清晰的系统提示词、4-5 个轻量数据工具，加上严格的输出护栏，就能覆盖大多数用例。

![子智能体设计](assets/f763118efed178629ae4672e83c2e2485367c3853f3a9de081d81c37cc1dd587.gif)

子智能体设计

需要说明的是，子智能体仍有其用武之地，包括在研究前沿。在以下情况使用它们：

- 单个智能体循环因上下文膨胀而出现可测量的性能下降，或
- 多个任务需要以全新的上下文窗口并行处理，且这些窗口在任务完成后即可丢弃，或
- 单个智能体难以选择合适的工具，或系统提示词中存在相互冲突的指令。

但我们太常看到企业为每个团队或每种问题类型都配一个子智能体，智能体架构变成了组织架构图的翻版（康威定律（Conway's law）在起作用）。

本文说明何时应考虑把子智能体并入主智能体循环，并分享我们在大型组织中构建智能体时总结的最佳实践。

## 大型组织中构建智能体的失败模式

公司往往想构建一个智能体，把多个产品和能力统一到单一客户界面中。

通常，每项能力由不同的团队负责，所以公司先让各个团队自行构建智能体，再由一个中央平台团队在上面构建编排器。这可以呈现为几种结构，包括编排器-子智能体（orchestrator-subagent），或把特定智能体作为 MCP 工具暴露出来的单一智能体。

这看起来是最简单的方案，却立即引入了以下方面的复杂性：

- **上下文管理（Context management）：** 你需要决定智能体之间交换哪些上下文，而且往往在这种来回传递中丢失细节。
- **子智能体泛滥（Subagent sprawl）**：每个团队都交付自己的子智能体，于是企业最终拥有数百个相互重叠的子智能体，既没有强制执行的标准，也没有明确的负责人。
- **弗兰肯提示词（The Frankenprompt）**：每个团队都往系统提示词里加一句话，导致规则相互冲突、语气不一致。
- **未经审核、过度局部化的评估（Unvetted, overly localized evals）**：每个人都添加自己的评估，且过度针对自己的子任务优化。没有人负责或维护整套评估，而管理层则基于被稀释、过度局部化的分数做决策。
- **延迟（Latency）**：多智能体架构的复杂性会增加延迟。一家客户将其多智能体 harness 与单一智能体循环做了对比评估，后者的运行时间约为前者的一半。

## 使用带渐进式披露的智能体循环

上面描述的编排器-子智能体设计，是协调跨团队构建的专家的一种合理方式，但通常更有效的做法是**通过技能（skills）渐进式披露上下文**，以及**通过工具搜索（tool search）渐进式披露工具**。换句话说，智能体只看到技能和工具的简短描述，只有在需要时才完整加载。

这种做法合理，原因有三：

- **共享上下文能带来更好的答案：** 对于运行时间较长的智能体，我们希望来自多个不同任务的上下文都留在主上下文窗口中。一个已经看到之前每一步结果的智能体能把它们联系起来，从而产生比一组子智能体交回的摘要更丰富的输出和更好的洞见。这也意味着[更少的上下文窗口和更少的有损交接](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)。
- **渐进式披露可防止上下文膨胀**：这一技术让团队可以构建单个智能体来完成各种各样的任务，而无需把所有上下文都立即装进一个冗长的系统提示词中。这消除了团队过去把工作拆分给子智能体的主要理由。事实上，我们[把 Claude Code 面向更高级模型的系统提示词缩减了 80% 以上](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)，其中就包括与渐进式披露技能和工具相关的削减。
- **模型能力更强**：从 Opus 4.5 开始，模型在单个循环中能处理的事情远超大多数团队的预期。在 Opus 5.5 和 Fable 5.1 上无法关闭 thinking，而且近期模型越来越会叙述自己的进展并边做边检查工作，这让某些 harness 元素变得多余。每一个新模型都让你能把更多决策从 harness 移到模型本身。更简单的循环也让整个系统更容易迁移到下一代模型；在我们帮助客户进行的迁移中，僵化的多智能体结构往往是阻碍新模型承担更多工作的原因。

单一智能体循环设计需要自律：精心管理的系统提示词、能在恰当时机触发的技能与工具描述，以及对上下文窗口、记忆和笔记的审慎处理。本文后续章节会进一步深入讨论迁移与设计考量。

应由一个中央团队负责端到端质量和系统提示词，在每个新工具和评估上线前进行审核。保持这个中央团队精干，有助于快速迭代，并降低大型组织内的协调成本。

如果你走多智能体路线，就从能起作用的最简单模式开始（生成器-验证器（generator-verifier）、编排器-子智能体（orchestrator-subagent）或其他）。通过**按上下文划分（dividing by context）：给每个子智能体一块几乎不需要系统其余部分配合的工作，让它交回一份紧凑的结果**来有效划分边界（好的候选是独立的研究路径、接口清晰的独立组件，或黑盒验证）。当智能体按问题类型拆分时，它们会玩起“传话游戏”（telephone game），信息来回传递，每次交接都会降低保真度。

## 如何将子智能体并入主智能体循环

许多团队的编排器和一组专家智能体已经在生产环境中运行。以下是我们建议朝之演进的单一循环设计：

- 一个模型、一个上下文窗口，运行开放式工具循环，并在 harness 中设置限制（轮次与成本预算、写入闸门（write gates））。
- 每一轮，模型发出一批工具调用。harness 并行执行这些调用，并把原始结果返回给同一个模型，由它决定下一步：再来一批、向用户提问，还是给出答案。
- 当模型给出答案或触及[预算](https://platform.claude.com/docs/en/build-with-claude/task-budgets)时，循环停止。可选地，在答案之后运行目标检查或验证器（verifier）检查。
- 模型在第一轮就把计划写进上下文中，并随着结果返回而修订它。这是相对于编排器加专家智能体配置的主要变化：写计划的模型同时也是执行计划的模型，因此它可以在轮次中途改变计划。
- 上下文仍然会被加载，并由智能体自己管理：
	- 不再需要那个根据规则目录重写计划的代码步骤，因为每一步由模型决定。
		- 排序和领域流程移入**技能**。
		- 硬性限制（校验、审批闸门）以及对话中途出现的任何其他事项（例如记忆查询）移入**工具**。
		- 代码仍可用于加载任何成本低廉且几乎总是相关的内容（例如实体解析步骤），以及在循环调用的工具内部处理任何机械性部分（构造载荷、解析流、恢复澄清流程）。

这种单一循环设计也有助于实现许多团队正在追求的最终目标状态（一个理解用户高层次目标并代其行动的智能体），因为它把智能体学到的一切都保留在同一个上下文中。

下面的建议说明了团队可以如何分阶段从多智能体系统过渡到单一智能体循环，以及多个团队如何在此过程中持续为该智能体做贡献。

### 任务完成度评估（Task-completion evals）

第一步是创建一个评估集，用来帮你判断是否应该把某个子智能体并入主智能体循环。我们见过的有效评估结构是：由中央团队负责一套共享的端到端评估集，同时每个技能附带由该技能所属团队负责的较小评估集。即使只有 10 个黄金样例，也足以起步。

按评分标准（rubric）给智能体的最终消息打分，是追踪答案质量的良好起点。在你仍有编排器时，还应追踪路由准确率（它是否选了正确的子智能体？）。一旦某个子智能体被并入，就改为检查智能体是否加载了正确的技能或调用了正确的工具。逐步转向任务完成度评估是有帮助的，因为在比较架构时，这一点最重要。

在内部系统难以重放、用户参与难以模拟的环境中，这可能很复杂。我们内部行之有效的一种做法是：为重要事件记录时间戳，以便之后重放，作为有针对性的评估来运行。

### 逐步减少子智能体

向单一智能体循环演进，涉及把子智能体并入工具和技能。这可以通过合并领域子智能体、把它们作为工具调用，或用技能和工具替换它们来实现。

### 合并领域智能体

在第一次合并前，先构建一个小型端到端评估。然后**按共享上下文并入，从使用最多的子智能体开始。**

[合并那些彼此串联、触及相同数据或经常被一起调用的专家](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)。例如，如果生产流量中有很大一部分是某个专家之后紧跟着第二个专家，那就是一对紧耦合的搭档，可以作为合并成一个领域智能体的候选。

### 作为工具调用的子智能体

当上述三个条件之一适用、而你仍保留某个子智能体时，让主智能体把子智能体作为工具调用可能很有效，这样它可以继续与用户保持对话。

只有当子智能体需要直接与用户对话时，我们才建议做完全交接（full handoff），即由子智能体接管对话。其他一切都可以是主循环中的一个技能加一些工具。

这样你就可以为子智能体定义共享的响应模式（response schema）、由主智能体用真实数据验证结论，并精简任何最终综合步骤的输入。这是很好的第一步，因为你不需要**重写**这些子智能体。它还能在决定把任何子智能体并入主智能体之前，为任务完成度评估提供**基线**。

不过，某些失败模式仍会存在：

- 每个专家都有自己的提示词、上下文、所属团队和评估
- 每次调用仍会交回有损的摘要
- 每次调用都是一个嵌套的模型循环，会增加延迟

### 通过技能和工具把子智能体并入主智能体

一次一个地把子智能体并入主智能体：把每个子智能体的提示词变成技能，把 API 调用变成 MCP 工具。比较有和没有该子智能体时的评估表现。然后决定保留哪些。

比较时不要只看最终分数，还要看看哪些任务的结果发生了翻转。当我们在一个示例支持智能体上测试时，把一个子智能体并入另一个子智能体虽然降低了延迟，却也破坏了一个原本一直通过的流程。主智能体持有订单查询工具并自行作答，没有向物流专家询问交付日期。

在每次改动前，确保你的评估中为生产环境中一起运行的每一条智能体链、以及智能体绝不能违反的每一条规则都准备了任务，并且每个任务运行不止一次，因为像这样的破坏只在两次运行中的一次里出现。

## 多个团队如何为单一智能体做贡献

领域推理可以从知识库、技能和 MCP 工具中检索。各个团队可以把自己的职责从智能体转移到技能和工具上，同时由一个小型中央团队保留对系统提示词和端到端质量的责任。这涉及在新技能、工具和评估上线前进行审核。

### MCP 工具

当智能体需要采取行动、从系统读取实时数据，或以固定格式返回结果时，工具是合适的选择。你也可以用工具作为迁移期间继续调用子智能体的方式。我们建议按用户意图对工具分组（而不是每个 API 一个工具），因为一旦系统提示词中的工具定义超过 30-50 个，工具选择能力往往会下降。

使用带延迟加载的[工具搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)，限制硬性前置条件，并把必要的前置条件移进工具中。例如，如果 Y 需要 X 的输出，Y 的工具会检查它，并返回一条模型可以照此行动的指令。按用户区分的权限也是同样的道理。每个工具都会检查发起调用的用户能看到什么、能做什么，并返回模型可读的简明拒绝信息，这样一个循环就能服务访问权限不同的用户，而无需为每个权限级别单独配置一个智能体。

### 技能

当智能体需要知道某个团队如何做事时——比如专家子智能体提示词过去承载的步骤、规则和判断——技能是合适的选择。

我们扩充技能库的方法是把维护工作交还给技能的编写者。Claude 可以借助那些能够构建、测试和修剪其他技能的技能来完成繁重的工作。

为防止技能泛滥，你可以让每个团队指定 DRI（直接负责人）负责自己的技能，确保它们制作精良、彼此区分，并附带适当的评估。

- **/skill-creator** 让你编写一开始就结构良好的新技能，并审计现有技能，对它们进行精简、去重和重构。
- **/skill-doctor** 让你看到技能库中每个技能的成本以及实际使用频率，并删除无用负担。

### 知识库

对于智能体只需要偶尔用到的参考资料，知识库是合适的选择。事实和参考资料（政策、指标定义、产品规格）可以放在模型调用的搜索或查询工具后面，也可以作为技能内的参考文件提供。避免让[代码检索上下文并粘贴到提示词中](https://claude.com/resources/articles/seeing-like-an-agent)。

## 加速这项工作的工具

我们最近[发布](https://code.claude.com/docs/en/commands)了一组 Claude API 技能，可以帮助完成上面提到的大部分工作。我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)把这些技能串联成一个引导式工作流，用于评估多智能体系统并将其迁移到单一智能体循环。它包含一个演示，你可以在真正动手前先试用：

- **/claude-api build-eval：** 可以帮助创建由中央团队负责的第一套端到端评估集，或各团队随其技能交付的小型评估集
- **/claude-api prompt-audit：** 可以标出你的提示词、技能和工具描述中为旧模型编写的指令，并以 diff 形式提出修复建议。可以对你的系统提示词运行它，找出那些为更早的模型添加、如今却让智能体变慢或变僵化的规则。各团队的 DRI 也可以对自己的技能和工具描述运行它。
- **/claude-api hillclimb：** 可以针对现有评估迭代改进应用。它可用于“并入 vs 保留”的比较（把一个子智能体并入技能加工具后，让它在技能和工具描述上迭代，看看并入版本是否能追平或超过子智能体），也可用于你的系统提示词。
- **/claude-api cost-optimize：** 分析你的调用都花在哪里，并逐项提出节省方案，例如提示词缓存、削减不需要的输入和输出 token、effort 以及模型选择。这有助于在给定设计上降低成本与延迟。

随着模型演进，我们对如何最好地使用模型的理解以及最佳实践指南也在演进。这使得任何一种架构都不如它背后的原则重要：测量、一次只改一件事、保留经得起检验的部分。
